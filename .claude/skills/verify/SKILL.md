# 머지 전 검증

검증 대상: $ARGUMENTS

인자가 비어 있으면 `git diff upstream/main...HEAD` 를 대상으로 삼는다.

## 원칙
- 이 Skill 은 **리뷰 세션**의 절차다. 코드를 수정하지 않는다. 고치기 시작하면 검증하는 쪽이 아니라 만든 쪽이 된다.
- 경로는 모두 저장소 루트 기준이다. 절차는 저장소 루트의 `templates/verification-loop.md`, 판정 항목은 저장소 루트의 `templates/approval-checklist.md` 를 따른다. 체크리스트 항목은 여기 옮겨 적지 않고 매번 그 파일을 읽는다.
- reviewer 또는 tester Sub-agent 가 없는 환경에서는 3번 · 4번을 기존 방식대로 메인 세션이 직접 수행한다.

## 절차

### 1. 요청 범위 확인
- 무엇을 요청받은 변경인지 한 문장으로 확인한다. 인자나 대화에서 찾을 수 있으면 그대로 옮겨 적는다.
- 찾을 수 없으면 **판정하지 말고** 사용자에게 먼저 묻는다. 답을 받기 전에는 2번 이후로 넘어가지 않는다.

### 2. 변경 파일 목록과 diff 읽기
- 목록을 먼저 본다: `git diff --stat <범위>` (patch 파일이면 `git apply --stat <파일>`).
- 그다음 파일마다 diff 를 읽는다: `git diff <범위> -- <파일>`. 판정에 필요하면 변경된 줄 주변의 원본 파일도 읽는다.
- 변경 파일을 `modern/api` · `modern/web` · `characterization` · 그 밖(`legacy/`, `db/`, `templates/` 등)으로 나눠 둔다. 4번에서 실행할 테스트가 이 분류로 정해진다.

### 3. 체크리스트 대조
- **reviewer Sub-agent 에 위임한다.** 메인 세션이 직접 대조하지 않는다.
- 넘길 것: 비교 범위(인자의 diff 범위 또는 patch 경로)와 1번에서 확인한 요청 범위 문장을 **고치지 않고 그대로** 넘긴다.
- reviewer 에게 아래 방식으로 대조하게 한다.
- 저장소 루트의 `templates/approval-checklist.md` 를 읽는다.
- 항목마다 **충족 / 미충족 / 확인 필요** 중 하나로 표시한다. 근거는 diff 의 `파일:줄번호` 로 댄다.
- 컨벤션 기준은 저장소 루트의 `CLAUDE.md` 를 쓴다. `convention-check` Skill 이 있으면 그 결과를 함께 쓴다.

### 4. 테스트 실행
- **tester Sub-agent 에 위임한다.** 메인 세션이 직접 실행하지 않는다.
- 넘길 것: 2번에서 나눈 변경 폴더 분류, 아래 표, 이 단계의 규칙(미실행 처리 · 사용량 절약).
- 새 로직(새 public 메서드 등)에 대응 테스트가 없으면 tester 가 테스트 파일을 추가한 뒤 실행하게 한다.
- 돌려받을 것: 실행 명령 · 통과 수 · 실패 수 · 실패한 테스트 이름, 추가한 테스트 파일 목록.

변경된 폴더의 테스트만 실행한다. 해당 폴더에 변경이 없으면 실행하지 않고 "해당 없음"으로 적는다.

| 변경된 폴더 | 명령 |
|---|---|
| `modern/api` | `cd modern/api && ./gradlew test` |
| `modern/web` | `cd modern/web && npm test` |
| 이관 코드 (레거시 → `modern/api`) | `cd characterization && npm test` (레거시 대상)<br>`cd characterization && TARGET_BASE_URL=http://localhost:8080 npm test` (새 API 대상) |

- 의존성이 없으면 `npm ci` 로 설치한다(`npm install` 은 쓰지 않는다).
- characterization 은 대상 서버가 떠 있어야 한다. 서버가 꺼져 있거나 의존성 설치가 안 돼 실행하지 못했으면 **통과로 쓰지 않는다.** "미실행"과 그 이유를 적고, 사람에게 기동을 요청한다.
- **사용량 절약:** 전체 로그를 대화에 싣지 않는다. 출력은 파일로 받고, 결과 요약만 뽑아 남긴다. 남기는 것은 **실행 명령 · 통과 수 · 실패 수 · 실패한 테스트 이름**뿐이다.
  - 예: `./gradlew test > <스크래치 경로>/api-test.log 2>&1; echo "exit=$?"` 를 실행한 뒤 `grep` 으로 `FAILED` 줄과 요약 줄만 읽는다.
  - 실패 원인을 설명해야 하면 해당 테스트의 assertion 메시지 몇 줄만 인용한다.

### 5. 승인 기준 판정
- reviewer 와 tester 의 보고를 모두 받은 뒤 **메인 세션이** 네 기준을 모두 최종 판정한다.
- 두 보고가 엇갈리면(예: reviewer 는 "테스트 없음", tester 는 "테스트 있음 · 통과") 엇갈린 지점과 양쪽 주장을 그대로 적고, 판정하기 전에 사람에게 묻는다.
- 네 기준(**테스트 통과 / 치명 이슈 0건 / 요청 범위 이탈 없음 / 컨벤션 준수**)을 하나씩 판정한다.
- 네 기준이 모두 충족이면 승인이다. 하나라도 미충족이면 반려다.
- 심각도 정의(치명 / 경고 / 제안)는 저장소 루트의 `templates/approval-checklist.md` 를 따른다.
- 요청 범위를 확인하지 못했으면 "요청 범위 이탈 없음"을 충족으로 표시하지 않는다.

## 출력 형식 (순서 고정)

```
판정: 승인 | 반려

| 기준 | 결과 | 근거 |
|---|---|---|
| 테스트 통과 | 충족 / 미충족 | 실행 명령 · 통과 수 · 실패 수 · 실패한 테스트 이름 |
| 치명 이슈 0건 | 충족 / 미충족 | 치명 이슈 번호 |
| 요청 범위 이탈 없음 | 충족 / 미충족 | 요청 문장 vs 변경 파일 목록 |
| 컨벤션 준수 | 충족 / 미충족 | 위반 이슈 번호 |

이슈 목록
| # | 심각도 | 파일:줄번호 | 근거 | 수정 방향 |
|---|---|---|---|---|
| 1 | 치명 / 경고 / 제안 | path/to/File.java:42 | ... | ... |

확인 필요
- (줄번호를 댈 수 없는 지적, 실행하지 못한 테스트를 한 줄씩)
```

- 이슈 한 건은 **심각도 · 파일:줄번호 · 근거 · 수정 방향** 네 칸을 모두 채운다.
- 수정 방향은 말로만 적는다. 패치나 수정된 코드를 붙이지 않는다.

## 하지 말 것
- 코드를 수정하지 않는다(tester 가 추가하는 테스트 파일은 예외). 보고만 한다.
- 근거 줄번호를 댈 수 없는 지적은 이슈로 올리지 않고 "확인 필요"로 남긴다.
- 테스트를 실행하지 않고 통과했다고 쓰지 않는다.
- 전체 테스트 로그를 대화에 붙이지 않는다.
